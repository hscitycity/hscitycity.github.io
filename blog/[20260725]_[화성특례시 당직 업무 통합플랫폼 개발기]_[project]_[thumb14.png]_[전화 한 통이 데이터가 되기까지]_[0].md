## 1. 왜 만들었나

2026년 4월, 인사혁신처가 당직제도를 **76년 만에** 전면 개편했다. 하지만 현장의 당직실 풍경은 크게 다르지 않다.

화성특례시의 당직은 2원 체계다 — 5층 재난안전상황실과 1층 시청 당직실. 상황실 당직자는 교대 때마다 한글 양식에 기상·특보·민원 접수내역을 손으로 옮겨 적는다. **회당 약 60분.** 그리고 그 기록은 문서 파일 속에 갇힌 채 다시는 데이터가 되지 못한다.

상습 민원지점이 어디인지, 평균 처리시간이 얼마인지 — 아무도 모른다. **통계가 없으니까.**

여기서 출발했다. 컨셉은 한 문장이다.

> **"사람이 받고, AI가 쓰고, 시스템이 처리한다."**

## 2. 무엇을 만들었나

| 기능 | 내용 |
|------|------|
| **AI 접수 서기** | 당직자가 통화하며 들리는 대로 막 적으면, AI가 신고유형·긴급도·위치를 분류해 접수 양식을 완성한다. 재난상황일지도 같은 방식 — 자유롭게 쓴 글이 보고서 표의 각 칸으로 정리된다 |
| **24시간 시민 민원접수창구** | 휴대폰 GPS 버튼 하나, 또는 지도를 눌러 핀을 꽂는 방식으로 신고. 위치를 말로 설명할 필요가 없다 |
| **실시간 GIS 상황판** | 접수 민원이 지도에 핀으로 뜨고, 가장 가까운 가용 인력을 자동으로 골라 실제 도로를 따라 출동하는 모습까지 보여준다. 담당부서 문자 인계도 클릭 한 번 |
| **공공데이터 12종 레이어** | 기상특보, 실시간 기상 관제(바람·비·번개), 미세먼지, 야간 병원, 범죄주의구간, 행사·인파, 도로 CCTV, 심야약국, 생활안전시설, 건축물대장, 지적도(필지 경계·지번), 항공사진 |
| **공문서 자동 생성** | 실제 쓰는 한글 양식 그대로, 일일보고와 민원접수서가 버튼 하나로 완성. 설치 없이 다운로드해 바로 결재 |
| **82쪽 당직메뉴얼 검색** | 종이 책자 대신 키워드 즉시 검색. 대응 절차는 번호순으로, 연락처는 바로 누를 수 있는 형태로 |
| **데이터 축적·분석** | 모든 접수·처리가 클라우드 DB에 실시간 저장. 종합현황 대시보드에서 추이·분야별·관할구별 통계 |

핵심은 마지막 줄이다. 앞의 기능들은 편의지만, **손으로 적어 문서에 갇히던 기록이 처음으로 "데이터"가 된다**는 게 이 프로젝트의 본질이다.

## 3. 기술 선택 — 왜 이렇게 골랐나

| 계층 | 선택 | 이유 |
|------|------|------|
| 화면 | 파일 하나짜리 웹앱 | 공무원 PC 어디서든 브라우저만 있으면 열림. 설치·빌드 없음 |
| 지도 | Leaflet + 국토부 VWorld | 공식 배경지도(일반·항공·야간)를 무료로 |
| AI | Claude API + 규칙기반 예비엔진 | AI가 응답 못 하는 순간에도 멈추지 않게 이중화 |
| DB | Supabase | 실시간 동기화와 데이터 API를 기본 제공 — 서버 개발 없이 |
| 배포 | Vercel | 코드를 올리면 1분 뒤 자동 반영 |

> 🏢 **비유**: 이 스택은 **"당직실 컴퓨터 한 대에서 바로 켜지는 것"**을 최우선에 뒀다. 아무리 좋은 시스템도 "설치하세요"부터 시작하면 현장에서 안 켠다. 브라우저 주소창에 주소만 치면 열리는 것 — 그게 공공 현장에서 도입률을 가르는 첫 관문이다.

이 원칙은 화성형 팔란티어 초기에 「왜 React가 아닌 단일 HTML로 시작했는가」에서 적은 것과 정확히 같다. 도입 장벽을 먼저 없애고, 고도화는 나중에.

## 4. 개발기에서 건진 것들 (삽질의 기록)

여기가 이 글의 본론이다. 되는 것보다 **안 됐던 것**이 더 많이 남는다.

### ④-1. 좌표 없는 주소검색

정부 주소검색 API는 주소는 주는데 **좌표를 안 준다.** 처음엔 해외 지도 서비스로 좌표를 찾았는데 한국 도로명 인식률이 낮았다.

**결론**: 국토부 좌표변환을 1순위로 하고, 실패하면 지번 → 해외 서비스 → 읍면동 중심 순으로 **4단계 예비 경로**를 쌓았다. 공공 API는 항상 예비 경로를 층층이 준비해야 한다.

### ④-2. 지도 키의 도메인 제한

공공 지도 API 키는 발급 때 등록한 사이트 주소에서만 동작한다. 파일을 그냥 더블클릭으로 열면 **조용히 거부**당하는데, 에러도 안 보여서 한참 헤맸다.

**해법**: 정식 배포(고정 주소 확보) + 요청이 실패하면 서버가 뭐라고 거절했는지 화면에 그대로 띄우는 자가진단 장치. **침묵하는 실패가 최악이다.**

### ④-3. 한 줄이 부른 대형사고

자동화 스크립트의 잘못된 한 줄이 **5MB 파일을 295MB로** 불려놓은 적이 있다. 다행히 복구했지만, 이후로는 결과물 크기가 정상 범위인지, 핵심 기능이 살아있는지를 **사람이 아니라 스크립트가 매번 검사**하게 했다.

> 🏢 **비유**: 이건 화성형 팔란티어 인프라 작업 때 배운 것과 같은 교훈이다. "기기를 옮기기 전에 push한다"처럼, **사람의 주의력에 기대는 안전장치는 언젠가 뚫린다.** 검사는 자동이어야 한다.

### ④-4. 웹 업로드의 함정

GitHub에 폴더를 드래그해 올렸는데 일부가 폴더가 아닌 **빈 파일**로 올라가서 자동화가 통째로 죽었다. 웹 업로드 후엔 반드시 구조를 눈으로 확인할 것.

### ④-5. 실시간의 배신

실시간 동기화 연결이 어떤 환경에서 **소리 없이 끊겼다.** DB엔 민원이 쌓이는데 화면은 멈춰 있는 상황. 상황실 시스템에서 이건 치명적이다.

**해법**: 실시간 연결 + 20초마다 확인하는 예비 경로 **이중화**. 실시간은 빠른 길일 뿐, 주기 확인이 보장된 길이다.

*(이 교훈은 며칠 뒤 화성형 팔란티어 본체 작업에서 그대로 반복됐다 — VPC 내부 DB도 "잘 돌아가는 것처럼 보이지만 실은 틀린 경로"였다. 겉으로 멀쩡한 게 가장 위험하다.)*

### ④-6. "고쳤는데 안 고쳐졌어요"의 정체

수정 배포를 거듭해도 같은 증상 제보가 왔는데, 알고 보니 브라우저가 **옛날 버전을 기억(캐시)**하고 있던 경우가 섞여 있었다.

**해법**: 화면 구석에 **빌드 버전 표기**를 넣고, 문의가 오면 첫 질문을 "버전이 뭐라고 떠 있나요"로 통일했다.

### ④-7. 공공 API 호출의 벽, 그리고 종전

공공 API 상당수는 브라우저에서 직접 못 부른다(보안 정책, CORS). 처음엔 남의 중계 서비스를 빌려 썼는데 불안정했다.

**최종형**: 우리 서버가 대신 불러다 주는 **자체 중계 창구 5종**을 만들고, 응답을 잠시 저장해뒀다 재사용하는 방식으로 공공 API 일일 호출량도 아꼈다.

*(브라우저에서 공공 API를 직접 못 쓰는 문제는 화성형 팔란티어 초기에도 똑같이 만났다 — 「브라우저에서 Naver API를 직접 못 쓰는 이유」. 결론도 같았다: 서버가 대신 불러준다.)*

### ④-8. 3.1GB 지적도를 웹에

화성시 필지가 **51만 개**다. 처음엔 일부 지역 표본만 넣었고, 다음엔 외부 지도서비스에 의존했다가, 최종적으로 **지도 조각(타일) 형태로 잘게 구워 직접 제공**하는 방식으로 전역 필지와 지번을 다 띄웠다.

용량 문제는 "덜 담기"가 아니라 **"다르게 담기"**로 푼다.

## 5. 자동화 — 언제 들어와도 살아있는 시스템

프로토타입의 고질병은 **"시연 때만 사는" 것**이다. 심사위원이 볼 때만 데이터가 있고, 평소엔 텅 빈 화면.

이 플랫폼은 DB에 심어둔 스케줄러가 **5분마다 가상 민원을 1건씩 자동 접수**한다. 시나리오 46종(전 분야 × 20개 읍면동)이 무작위로 순환하고, 좌표도 매번 조금씩 다르게 생성된다. 시나리오는 AI 에이전트가 계속 새로 써서 공급한다.

접속할 때마다 민원이 흐르고 대시보드가 두꺼워지는, **운영 중인 시스템.** 이건 화성형 팔란티어의 water-demo가 "시나리오 재생"에 그쳤던 것에서 한 걸음 나아간 형태다 — 시연이 아니라 상시 가동이다.

## 7. 배운 것 한 줄씩

- 공공 API는 **예비 경로를 층층이 쌓는 게 기본기**
- **침묵하는 실패를 없애라** — 오류는 화면에, 버전은 구석에, 검사는 자동으로
- **실시간은 빠른 길, 주기 확인은 보장된 길.** 상황실엔 둘 다
- 용량 문제는 **덜 담는 게 아니라 다르게 담는 것**
- 그리고: **현장에서 쓰던 양식을 그대로 살리는 것**이 도입 장벽을 없애는 가장 빠른 길이었다

마지막 줄이 가장 크다. AI 접수 서기가 아무리 똑똑해도, 결과물이 당직자가 늘 쓰던 그 한글 양식으로 안 나오면 안 쓴다. **기술이 현장에 맞추는 것이지, 현장이 기술에 맞추는 게 아니다.** 이 순서를 지킨 것이 431건이 쌓이는 동안 시스템이 살아있게 한 이유다.
